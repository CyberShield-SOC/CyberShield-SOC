## Deployment and CI/CD architecture

The React/Vite frontend builds into `frontend/dist`; FastAPI serves the API and the built UI from one application. PostgreSQL stores upload batches, parsed logs, alerts, incidents, users, and notes. The production web process must bind to Railway's `PORT` and run Alembic migrations before serving traffic. Railway PostgreSQL must supply `DATABASE_URL` in SQLAlchemy's `postgresql+psycopg://` form; the URL is a secret, never a `VITE_*` variable. `JWT_SECRET_KEY` and initial Admin credentials are also server-only secrets. Set `AUTH_COOKIE_SECURE=true` on the HTTPS public domain. Restrict service access to the intended domain, and use the same-origin `/api` path for the browser.

GitHub Actions in `.github/workflows/ci.yml` runs on pushes and pull requests to `main`. The backend job starts PostgreSQL 17, installs Python dependencies, applies migrations, and runs pytest. The frontend job installs pinned npm dependencies with `npm ci`, runs tests, builds the site, and uploads the static build artifact. A green CI run is a merge prerequisite. Deployment should follow the reviewed merge, with a post-deploy health and authenticated upload smoke test. No Railway service, secrets, or live URL are recorded in this checkout, so production verification is still an operational step.

## Upload and detection flow

An authorized Analyst/Admin uploads a log file. The backend validates it, parses and normalizes event fields, runs the configured detection engine, and persists upload metadata, logs, and alerts together. The new `multi_ip_successful_login` rule checks distinct source IPs for successful logins to one account within 300 seconds (default threshold 3). The new `sudo_after_login` rule correlates a successful login with successful privilege escalation for the same account within 120 seconds. Both rules are configurable through `DETECTION_RULE_CONFIG`; the rule metadata API exposes active thresholds. These are triage signals, not proof of compromise: VPN egress changes and legitimate administration can cause false positives. The suspicious and normal CSV files in `sample-logs/kk_*.csv` provide repeatable parser-and-engine checks.

## ML architecture and evaluation plan

The first ML use case should rank anomalous authentication activity after deterministic rules run. Build per-account and per-source-IP time-window features: failed/successful login counts, distinct IP count, distinct account count, time since prior login, privilege-escalation count, hour-of-day, and parser-quality flags. Use `upload_id` plus `line_number` as event identity and event timestamp for windows; retain ingestion time separately. Require a dataset with normal and suspicious examples across supported formats and known time periods, including both fixtures and independently collected, permissioned logs. Split evaluation by time and upload batch to prevent near-duplicate events from leaking across train and test sets. Exclude raw secrets and personally identifying free text from model input.

Start with an interpretable unsupervised Isolation Forest baseline because confirmed incident labels are not yet established. Compare it against a rule-only baseline. Once analysts review enough incidents, evaluate a supervised model with adjudicated labels. Report precision, recall, PR-AUC, false alerts per 1,000 events, and detection latency; tune thresholds on validation data only. Review errors by log source, account type, and parser completeness. Persist model version, feature schema, score, threshold, and top contributing feature values alongside future anomaly results so analysts can explain and reproduce a finding. The planned integration point is after normalization and before alert persistence; the existing rule engine remains independently available if an ML model is unavailable.
